# ArkheKernel v0.15.0 Epoch — Design Blueprint (CIL)

> Generated by the multi-architect adversarial design workflow (4 angles, 16 judges, synthesis).
> Winning spine: **Canonical Input Log**. Ranking: input-log=8.13, effect-log=7.63, minimal-wire=7.50, first-principles=7.38.

## ArkheKernel v0.15.0 Epoch — The Canonical Input Log (CIL): record exogenous inputs + verdicts, re-derive every effect by deterministic re-execution

## Core spine

The single unifying model is the Canonical Input Log (CIL). The v0.14 WAL conflates three distinct facts into one "record per committed pop_due": (a) the exogenous admission of an external action, (b) the internal derivation that a parent's compute() scheduled a child, and (c) the durable proof a step committed. All six audited symptoms are consequences of that conflation. CIL separates them: the WAL records ONLY the non-reproducible facts — external Submit inputs and per-pop Step verdicts+post-state-digest — and RE-DERIVES everything deterministic (child schedules, signal routing, refcount deltas, internal id allocation) by re-executing compute() during replay. This is sound because the transition is already pure: #![forbid(unsafe_code)], no async/thread, saturating arithmetic, BTreeMap/BTreeSet only, !Sync single-threaded. The decisive reason CIL beats the effect-log runner-up: the effect-log's apply-only replay starts the scheduler from next_seq=0 and can never reconstruct the scheduler's next_seq FIFO tie-breaker (scheduler.rs:70,103-104) — it is in InstanceSnapshot but in NO per-step wire field and is NOT derivable from schedule_deltas — so same-tick pop order, record order, and the chain DIVERGE (a real A1 break the effect-log judges flagged as fatal). Under CIL, next_seq and next_id are never wire state: replay re-runs the identical schedule()/schedule_with_id() call sequence in the identical order, so both counters advance bit-identically by construction. CIL also makes double-execution UNREPRESENTABLE (internally-scheduled children are never Submit records — they only re-materialize as a side-effect of the parent's re-executed compute(), then surface once as their own Step record), makes denials first-class (a Step with a Denied verdict), makes signal half-commit impossible (no persisted-but-undelivered intermediate exists; routing is a re-executed effect), makes capability time-shift unrepresentable on the wire (action_principal is deleted from Op::ScheduleAction; the child principal is DERIVED from the executing parent), and makes replay self-verification a genuine proof (each Step's full-state post_state_digest is measured from the replayed kernel and asserted, plus the chain tip is measured from a replay-side WalWriter, never copied). The honest tell that this is the right reframe: the per-record body SHRINKS — 11 effect fields collapse to inputs+verdict+digest, and the common Submit record carries no StepStage at all.

## Replay algorithm

Replay RE-EXECUTES compute(); it NEVER applies recorded effects and NEVER copies the chain tip. The chain holds two record kinds discriminated by WalRecordKind (kind is the FIRST hashed body field). Driver (replay_records), header gates + chain verify run first exactly as today, THEN:

```
let mut writer = WalWriter::rebuild_from_header(&wal.header);   // replay-side writer, prev_hash=0, same chain_key
for rec in &wal.records {
  match rec.kind {
    Submit => {
      // Exogenous admission. Re-inject with the SAME id the original minted.
      kernel.submit_with_id(rec.instance, rec.principal, rec.actor, rec.caps_at_submit,
                            rec.allocated_id, rec.at, rec.action_type_code, rec.action_bytes.clone())?;
      // Submit does NOT step. caps_at_submit rides directly onto the scheduled entry as its caps_ceiling
      // (no separate caps table) so the child authorizes under effective_caps & caps_ceiling when it pops.
    }
    Step => {
      // Pop EXACTLY the due entry, re-run deserialize->compute->authorize->dispatch->apply-or-rollback->route->deliver,
      // under the operator session ceiling RECORDED on the Step record (rec.session_caps), reproducing effective_caps verbatim.
      let outcome = kernel.process_instance_record(rec.instance, rec.now, rec.session_caps, /*measure_digest=*/true);
      // Determinism tripwires (fail-fast at the FIRST diverging step, not silent tail corruption):
      ensure!(outcome.popped_id == rec.popped_id,  PoppedIdDivergence{at: rec.seq});   // scheduler order witness (covers next_seq)
      ensure!(outcome.verdict   == rec.verdict,    VerdictDivergence{at: rec.seq});    // path-determinism witness
      ensure!(kernel.state_digest(rec.instance) == rec.post_state_digest, StateDigestDivergence{at: rec.seq}); // A1 witness, FULL-STATE
      // Re-append into the replay-side writer from the SAME inputs/verdict to MEASURE (not copy) the chain.
      writer.append_step(rec.instance, rec.popped_id, rec.now, outcome.verdict, kernel.state_digest(rec.instance))?;
    }
  }
  // For Submit records, mirror append_submit into the replay writer too, so the rebuilt chain covers both kinds.
}
report.final_chain_tip = writer.chain_tip();                          // MEASURED, not wal.chain_tip()
ensure!(report.final_chain_tip == wal.chain_tip(), ChainTipDivergence); // load-bearing, in-epoch A1 witness
```

External vs internal distinction needs no flag: external admissions are Submit records; internal schedules are NOT logged — they reappear when the parent's Step re-executes compute() and dispatch re-stages Op::ScheduleAction. A child surfaces only as its own Step record (its execution). Thus a child is scheduled exactly once (parent re-exec) and executed exactly once (its Step) — double-execution is structurally impossible.

Denials are real Step records: AuthDenied (whole-stage rollback) re-runs the same authorize path and reaches the same verdict because caps/principal/state are reconstructed identically; the post_state_digest pins the post-rollback state (scheduler entry consumed via pop_due, no entity/component mutation) so the consumed id AND the unchanged state are both verified. BudgetPartial{denied:u32} is the partial-commit path (per-Op budget skips push EffectFailed and do NOT roll back — kernel.rs:438-444); its Step record carries a non-empty re-derived stage and the digest pins the committed siblings. Committed/AuthDenied/BudgetPartial are three distinct verdicts so the partial-commit case is never conflated with whole-stage rollback. Unregistered and DeserFailed are Skipped{reason} verdicts (the original advanced actions_executed but committed nothing); replay re-runs registry lookup/deserialize and re-reaches Skipped (replay re-registers the same actions, so a Skipped verdict is reproduced only because step_one trusts the pop and re-derives — the digest pins that no state changed).

Determinism foundation: compute() is pure over a read-only &Instance ActionContext returning Vec<Op>; all arithmetic saturating; iteration BTreeMap/BTreeSet only; caps/principal/tick/actor reconstructed from records; scheduler (at,seq,id) order reproduced because schedule/pop call order is reproduced. The only non-derivable inputs are the Submit fields and per-Step now — all in the WAL.

## Scheduling / ID model

ScheduledActionId becomes canonical via a single allocation authority per instance, captured-for-externals and re-derived-for-internals — the counter is never re-minted from a possibly-drifted state on replay.

EXTERNAL submits: submit() mints the id from id_counters.next_scheduled exactly as today (kernel.rs:314-316), but the minted id is now WRITTEN into the Submit record's allocated_id field. Replay calls submit_with_id(allocated_id) — the plumbing already exists (Scheduler::schedule_with_id, scheduler.rs:128, which bumps next_id to max(next_id, id) at lines 137-139) — so the id is reproduced verbatim. id_counters.next_scheduled is advanced to allocated_id on the replay submit so subsequent allocations stay monotonic. This closes drift symptom #2 for the external path; the recorded allocated_id is the irreducible kernel-decided fact.

INTERNAL schedules (Op::ScheduleAction): the id is NOT user-supplied and NOT logged. It is re-derived during the parent's Step re-execution. The existing per-action local next_scheduled_id (kernel.rs:381, dispatch.rs:105, seeded from id_counters_snapshot().next_scheduled) is retained, and the v0.15 fix LANDS the flagged latent bug at apply.rs:133-149: the Add path currently throws away the staged entry.id and calls scheduler.schedule() which RE-MINTS a fresh id — a divergence waiting to happen. v0.15 changes that one branch to scheduler.schedule_with_id(entry.id, entry.at, entry.actor, entry.principal, entry.action_type_code, entry.action_bytes), making the staged id the committed id end-to-end (dispatch -> stage -> apply -> scheduler). Because the seed (counter), the order (compute() Op order), and the per-op increment are all deterministic and reproduced on replay, internal ids are bit-identical without ever being logged.

THE next_seq / next_id RESOLUTION (the effect-log's fatal hole, structurally absent here): next_seq (FIFO tie-breaker, scheduler.rs:70) and next_id (scheduler.rs:72) are advanced ONLY through schedule()/schedule_with_id()/pop_due(). Under CIL replay re-runs those exact calls in the exact order (external submits via submit_with_id, internal schedules via apply's schedule_with_id, pops via step_one's pop_due), so both counters advance bit-identically. They are NEVER wire state and need no new field — re-execution reproduces them. This is precisely why apply-only replay could not work and re-execution can.

DENIED/SKIPPED steps and the id sequence: every pop_due (commit OR denial OR skip) is now a first-class Step record, so the consumed seq/id ordering is fully represented. A denied step that consumes an id but mutates no entity/component state is fully reconstructable: its Submit (or parent-derived schedule) created the entry, its Step record (verdict=AuthDenied) records the consumption via popped_id, and post_state_digest pins the resulting counters. Each Step's full-state digest includes next_seq, next_id, and id_counters, so any drift fails fast at the first diverging step rather than silently corrupting the tail.

IdCounters.next_source_seq is confirmed genuinely dead (never set nonzero in any live path: only stage.rs:120 / apply.rs:45-47 plumb a zero advance). It is OUT OF SCOPE for this epoch — left untouched to keep the change minimal; removing it is deferred to a future wire-neutral cleanup, not bundled into the epoch.

## Signal model

SendSignal becomes a complete, re-executed, refcount-conserving effect with a real delivery target — the half-commit is eliminated by deleting the persisted-but-undelivered intermediate, not by patching the drain.

New canonical per-instance state (added to Instance AND InstanceSnapshot, epoch-permitted): signal_inbox: BTreeMap<RouteId, VecDeque<InboundSignal>> where InboundSignal { from: InstanceId, principal: Principal, payload: Bytes, seq: u64 }. A per-instance inbox_seq: u64 gives deterministic intra-route ordering. InstanceConfig gains max_inbox_per_route: u32 (0 = unlimited, matching the existing max_scheduled convention). BTreeMap+VecDeque is deterministic and BTree-only-clean; inbox_seq pins VecDeque order.

Routing runs identically in step()'s post-apply phase AND in replay's step_one (it is the SAME shared router function, factored once — see the dual-path refactor in implementation_steps). apply_stage now DRAINS pending_signals (closing the dangling list at apply.rs that today never touches it). The cross-instance borrow hazard (step() holds one iter_mut across instances, kernel.rs:344-353) is resolved the ONLY borrow-legal way: per-instance apply returns a delivered: Vec<(InstanceId, InboundSignal, RouteId)>; the kernel commits deliveries AFTER the iter_mut loop, walking targets in ascending (sender InstanceId, target InstanceId, route, inbox_seq) order. Self-delivery (target == sender) is applied inline. This introduces a documented, deterministic ONE-STEP delivery latency for cross-instance signals (deliveries land before the next step) — a real semantic change that is replayable and digest-pinned, called out as an open decision and covered by a dedicated test.

Per staged PendingSignal { target, route, payload, principal }: resolve target in the instance map. If target exists and its inbox for route is below max_inbox_per_route -> push InboundSignal (seq = target.inbox_seq++), and stage inflight_refs_delta[route] += 1 AT DELIVERY (not speculatively in dispatch), and emit KernelEvent::SignalDelivered{ from, target, route } (NEW variant, next free EventMask bit 1<<10; ALL 0x3FF -> 0x7FF). If target missing -> KernelEvent::SignalDropped{ target, route, reason: TargetNotFound } (the variant ALREADY EXISTS, event.rs:64, with SIGNAL_DROPPED mask 1<<5) and NO refcount increment. If inbox full -> SignalDropped{ ..., QueueFull } (reason exists, event.rs:111), no increment.

Refcount lifecycle becomes a conserved quantity (closing the root cause: today dispatch.rs:135 increments unconditionally and apply commits it with no delivery and no decrement): increment happens ONLY on successful enqueue (delivery), so a dropped signal increments nothing and leaks nothing. Decrement happens when the receiver consumes the inbound signal (a future RecvSignal/DrainSignal op, RESERVED this epoch, not minted — no scope creep) or when force_unload drains the route (the real existing drain at kernel.rs:272). Invariant: Σ deliveries − Σ (consumes + unloads) = live undelivered signals; the refcount can never be permanently incremented without a matching inbox entry. Note this epoch lands the delivered-side increment with consume deferred, so a delivered-and-unconsumed signal holds a live ref until force_unload — that is a complete, balanced lifecycle for the paths that exist, not a half-commit (the dropped paths balance exactly, the delivered path balances via the existing unload drain).

Replay: signals are fully re-derived — Op::SendSignal reappears when the sender re-executes, the shared router re-routes, inbox + refcount + events re-produce identically. NOTHING about signals is separately logged; pending_signals stays transient stage scratch (already excluded from the chain — correct) but is now DRAINED at apply. The post_state_digest is measured PER INSTANCE at that instance's own step (it covers the signals that instance has RECEIVED into signal_inbox/inbox_seq plus its inflight_refs) and is captured in step_one_core BEFORE the router runs — which is correct, because the router mutates the *target* instances, never the sender, so a sender's own digest is unaffected by its outbound routing. A signal delivered to an instance is therefore witnessed by that RECEIVER's next Step digest (a self-send, or a same-round target that already stepped, lands one step later — the documented one-step latency). Bit-identity does not rest on the digest alone: routing is a pure deterministic function of the re-derived pending_signals, so replay reproduces every delivery identically regardless of which deliveries a given digest happens to witness; the digest is a strong per-instance witness and the final MEASURED chain tip is the end-to-end one. (signal_routing_replays_bit_identical exercises a cross-instance delivery to a non-stepping target and still replays to an identical tip.)

## Capability model

Capabilities bind to the (instance, principal) pair at EXECUTION time, derived from per-instance config, never minted by domain code. This makes the dead InstanceConfig.default_caps (config.rs:19) load-bearing and removes the Principal::System blanket bypass (authz.rs:118).

1. effective_caps resolution. step_one no longer takes a single global caps argument as the authority. For an executing action it computes effective_caps(default_caps, principal, ceiling) = (default_caps ∩ ceiling) for every AUTHENTICATED principal, empty for Unauthenticated — a uniform min-of-bounds (the SAME shape as the existing A10 quota reduction). The ceiling is the inherited bound: caps_at_submit for an externally-submitted root, or the scheduling parent's effective caps (caps_ceiling) for an internally-scheduled child.
   - Principal::System: effective = default_caps ∩ ceiling. NOT an unconditional bypass and NOT exempt from the ceiling — System is privileged only insofar as default_caps grants AND the ceiling permits. (An earlier sketch had System = default_caps alone, ignoring the ceiling; that silently let a scheduled System child re-widen past its parent's caps_ceiling when the operator session ceiling was raised between parent and child execution — a time-shift escalation. Applying the ceiling to System too closes it: a System child is locked to its parent's effective caps exactly as an External child is. The kernel-internal origin distinction is carried by the principal TAG and by direct-API scheduling (point 4), not by a capability bypass.)
   - Principal::External(_): effective = default_caps ∩ ceiling, where for a root the ceiling = caps_at_submit (the bounded grant recorded on the Submit record).
   - Principal::Unauthenticated: empty (deny-all, unchanged).

2. authorize() stops treating Principal::System as all-bypass. The System arm performs the SAME match_op_cap(op, effective_caps) check as External, against the System principal's effective_caps (= default_caps). Kernel-internal origins that legitimately need SYSTEM run against instances whose default_caps include SYSTEM; a domain module cannot manufacture authority it was not configured to hold. This closes the authz.rs:118 blanket bypass at the root.

3. Op::ScheduleAction.action_principal is REMOVED from the ABI (op.rs:72-73). This is the leanest possible fix for the time-shift channel — a field DELETION that closes the escalation path at its source (dispatch.rs:114 currently stamps it verbatim) rather than policing it downstream. The scheduled child's principal is DERIVED from the scheduling context: the child inherits the executing action's principal, captured at dispatch time from effect.principal (already in scope, dispatch.rs:30). There is no channel left for an action to mint a System-principal future action — privilege can only DECREASE across a schedule (inherit-and-narrow, monotone-safe). The scheduled entry additionally captures caps_ceiling: CapabilityMask = the effective_caps under which the parent ran; when the child later pops it authorizes under effective_caps(child) ∩ caps_ceiling, so no path can re-widen. caps_ceiling rides inside ScheduledEntry (which is in InstanceSnapshot and, on the live path, only in transient stage — NOT in any per-record WAL body, because schedules are never logged under CIL), so it is snapshot-wire only, not a per-record chain cost.

4. Legitimate System-origin scheduling (cleanup cascade, signal relay) is performed by the KERNEL itself through an internal API that constructs the ScheduledEntry directly, NOT through the domain Op surface (preserving Mechanism != Policy; principal.rs already documents System as init/signal-relay/cleanup/replay-re-injection origin).

5. The step() caps argument is retained as an operator session ceiling (a further intersection: effective ∩ session_ceiling) so an operator can throttle BELOW config but never grant ABOVE it. The session ceiling is a non-reproducible operator input at step time — exactly the same kind of fact as caps_at_submit at submit time — so for input-log completeness it is RECORDED on the Step record as session_caps:u64 and reconstructed verbatim on replay. effective_caps is then reproduced exactly and EVERY history replays bit-identically, including those run under an operator throttle. (This supersedes an earlier sketch that omitted session_caps and replayed with CapabilityMask::all() relying on the verdict assert to merely *catch* a divergence; that left throttled histories non-replayable. Recording the one field closes that gap and keeps the CIL principle consistent — record every non-reproducible input, re-derive everything else. It is Step-body only, ~8 bytes/step.) Child caps still come from execution context (effective_caps ∩ caps_ceiling), NOT from a submission_caps[popped_id] table that has no entry for internally-scheduled children — that record exists ONLY for externally-submitted roots.

## Wire format

Epoch advance: frozen Layer A surfaces change deliberately and minimally; each change is tied to the Layer A item it touches and the problem it solves. POSTCARD_MAJOR and BLAKE3_MAJOR are held (codec/hash generation unchanged).

A) DOMAIN_CTX literal (wal.rs:85): b"arkhe-kernel v0.14 ..." -> b"arkhe-kernel v0.15 WAL chain domain separation context". Verified to be 54 bytes (so the .len() == 54 assertion at wal.rs:1037 is UNCHANGED). Required because the body shape changes — every chain key MUST rederive to prevent cross-epoch chain confusion. This intentionally invalidates all v0.14 WALs (forward-only, pre-public — permitted).

B) Header version pins (wal.rs:71-73): CURRENT_KERNEL_SEMVER (0,14,0) -> (0,15,0); ABI_VERSION (0,14) -> (0,15). POSTCARD_MAJOR/BLAKE3_MAJOR unchanged. domain_separation_context Vec follows (A).

C) WalRecordBody — the central restructure. Replace the 11-field execution-effect body with a kind-discriminated input/verdict body. The body is a borrowed enum WalRecordBody whose serde variant tag is the kind — WalRecordKind { Submit, Step } — so the kind is the FIRST hashed byte. prev_chain_hash is folded into the body as the LAST hashed field of each variant (so reordering records breaks the chain); note the keyed chain hash ALSO prepends prev standalone in seal(), so prev binds the link twice — its position inside the body is a tamper-binding detail, not a chain-linkage one.
   Submit body (hashed, in order): kind, seq, instance, principal, actor, caps_at_submit:u64, at:Tick, action_type_code:TypeCode, action_bytes:&[u8], allocated_id:ScheduledActionId, prev_chain_hash:[u8;32].
     — actor is RETAINED (it feeds ActionContext::actor and compute() branches on it; dropping it is a determinism hole — this fixes the input-log layout omission).
     — caps_bits is renamed caps_at_submit and lives on Submit only.
   Step body (hashed, in order): kind, seq, instance, popped_id:ScheduledActionId, now:Tick, session_caps:u64, verdict:StepVerdict, post_state_digest:[u8;32], prev_chain_hash:[u8;32].
     — session_caps records the operator session ceiling in force (see capability-model point 5) so the verdict is re-derivable on replay.
   The stage: &StepStage field is REMOVED entirely from the body — the staged effect is re-derived, never persisted. This is the single largest, most deliberate change and the structural realization of "record inputs+verdict, re-derive effects"; dispatch.rs builds the entire StepStage purely from compute() output, so hashing it was pure redundancy. The body genuinely SHRINKS.

D) StepVerdict enum (hashed in the Step body), SUBSUMING and replacing AuthDecisionAnnotation (wal.rs:88-98, the old 2-variant enum is DELETED — net field reduction, not addition): Committed | AuthDenied | BudgetPartial{denied:u32} | Skipped{reason:SkipReason} where SkipReason { Unregistered, DeserFailed }. AuthDecisionAnnotation cannot carry Unregistered/DeserFailed/partial-counts, so this richness is structurally mandatory.

E) post_state_digest derivation: BLAKE3 over the instance's FULL canonical post-step bytes in a fixed field order. It is realized by REUSING the existing InstanceSnapshot Serialize — blake3(postcard(self.to_snapshot())) — so the fixed order IS the InstanceSnapshot declaration order: id, config, entities, components, scheduler (key-set + next_seq + next_id), id_counters (incl. next_source_seq), ledger, inflight_refs, signal_inbox, inbox_seq, wall_remainder, local_tick. Reusing the snapshot (rather than a separate digest-only projection) means id and config are hashed too; that is harmless — both are constant per instance across a run, so they can neither mask nor manufacture a divergence — and it keeps a single canonical serialization for both snapshot/restore and the digest. MUST be full-state (not a counters-only fast path): under CIL the body no longer carries entity/component bytes, so a counters-only digest would leave entity/component divergence undetected and silently reopen problem #4. Zero HashMap (all Instance state is BTreeMap/VecDeque/scalar).

F) WalRecord stored struct (wal.rs:102-144) mirrors the body: kind, the kind-specific fields, prev_chain_hash, this_chain_hash, signature, signature_pqc. Signatures still cover the same body bytes (no signing-pipeline change).

G) Op::ScheduleAction loses action_principal (op.rs:72-73) — ABI Op wire change (capability fix at the source). ScheduledEntry (scheduler.rs:52-62) gains caps_ceiling: CapabilityMask — snapshot wire only (schedules are never per-record WAL state under CIL).

H) Instance/InstanceSnapshot (instance.rs:34-53, 266-278) gain signal_inbox: BTreeMap<RouteId, VecDeque<InboundSignal>> and inbox_seq: u64; InstanceConfig (config.rs:16-35) gains max_inbox_per_route: u32. New InboundSignal type (state side). Snapshot wire advance, epoch-permitted; KernelSnapshot has no schema_version field today, so no version-pin churn there.

I) KernelEvent gains SignalDelivered{ from, target, route } (event.rs) + EventMask::SIGNAL_DELIVERED = 1<<10, ALL 0x3FF -> 0x7FF, matches() arm added. SignalDropped + SIGNAL_DROPPED (1<<5) and SignalDropReason already exist — reused.

All four BLAKE3 frozen-hex regression pins (wal.rs:1040 DOMAIN_CTX hash, 1126 record layout, 1209 chain hash, 1239 hybrid layout) are REGENERATED once as epoch anchors and re-pinned — they are epoch baselines, not cross-epoch invariants.

## Layer A escalations

Three Layer A items advance; each needs the full 8-field escalation record (per feedback_l0_sealing_two_layers — Layer A items 1..7 are catastrophic invariants with an escalation pathway; an epoch is the sanctioned advance event). The 8 fields: (1) item id, (2) old value, (3) new value, (4) trigger, (5) blast radius, (6) reversibility, (7) regenerated anchors, (8) human sign-off.

ESCALATION #1 — DOMAIN_CTX literal (Layer A item 1, byte-identity invariant). old: b"arkhe-kernel v0.14 WAL chain domain separation context" (54B, BLAKE3 4c20c4...1fda). new: b"arkhe-kernel v0.15 ..." (also 54B; BLAKE3 regenerated at impl time). trigger: WalRecordBody shape change (C) forces a chain-key rederive to prevent cross-epoch chain confusion. blast radius: every v0.14 WAL becomes unreplayable under v0.15 (forward-only, pre-public — zero external cost). reversibility: forward-only by design; reverting requires re-pinning v0.14 string. anchors: wal.rs:1035-1041 (EXPECTED + FROZEN_HEX) regenerated together. sign-off: REQUIRED (catastrophic-invariant advance).

ESCALATION #2 — Header version pins (Layer A version-pin item). old: CURRENT_KERNEL_SEMVER=(0,14,0), ABI_VERSION=(0,14). new: (0,15,0), (0,15). trigger: minor bump = wire-format epoch per the project versioning scheme. blast radius: replay header gates (replay.rs:120-131) reject all v0.14 headers. reversibility: forward-only. anchors: wal.rs:71-73 + header test wal.rs:872. POSTCARD_MAJOR/BLAKE3_MAJOR HELD (no codec/hash-generation change — the granularity discipline). sign-off: REQUIRED.

ESCALATION #3 — WalRecordBody field order/contents (Layer A item: frozen field order). old: 11-field effect body with stage + caps_bits + auth_decision. new: kind-discriminated Submit/Step body, stage REMOVED, AuthDecisionAnnotation -> StepVerdict, +popped_id/allocated_id/caps_at_submit/post_state_digest, actor RETAINED. trigger: the CIL root model (record inputs+verdict, re-derive effects). blast radius: the chain hash, the WalRecord struct, append(), verify_chain(), WalRecordBody::from_record, every frozen-hex test. reversibility: forward-only. anchors: wal.rs:1116-1132 (record layout), 1189-1214 (chain hash), 1236-1243 (hybrid layout) ALL regenerated and re-pinned. sign-off: REQUIRED (largest single Layer A surface change of the epoch).

NOT escalated (held within their non-Layer-A status): Op::ScheduleAction field removal (ABI Op, #[non_exhaustive], not a frozen-byte Layer A anchor); ScheduledEntry.caps_ceiling, signal_inbox/inbox_seq/max_inbox_per_route (snapshot wire — epoch-permitted, KernelSnapshot is versioned alongside but has no frozen-byte test); KernelEvent::SignalDelivered (#[non_exhaustive] enum, external-safe).

## Open decisions

- MANIFEST VALIDATION ON DEFAULT PATH (problem #4 residual): replay_into today trusts the header's manifest_digest; making validation mandatory couples the epoch to type_registry_pins, which is an EMPTY/deferred slot (wal.rs:53-54). RECOMMENDATION: on the default replay_into, validate the header manifest_digest against the running kernel's reconstructed ModuleManifest digest (a self-consistency check that needs no TrustAnchor), and KEEP TrustAnchor mandatory only for untrusted inputs via replay_into_verified. Do NOT block the epoch on populating type_registry_pins — keep that deferred. Confirm this scope boundary.
- ONE-STEP CROSS-INSTANCE SIGNAL LATENCY: the borrow discipline (single iter_mut over instances, kernel.rs:344-353) forces cross-instance deliveries to land after the sender's step, before the next step. This is a real, observable semantic change (self-delivery is inline; cross-instance is +1 step). RECOMMENDATION: accept it (it is the only borrow-legal, A2-respecting, deterministic option and is digest-pinned + tested). Confirm the latency semantic is acceptable for L2 IPC consumers.
- REFCOUNT DELIVERED-SIDE DECREMENT (RecvSignal/DrainSignal): this epoch lands increment-on-deliver and decrement-on-drop/unload, but the receiver-side consume op is RESERVED, not minted (no scope creep). A delivered-and-unconsumed signal holds a live inflight_ref until force_unload. RECOMMENDATION: ship the conserved-on-drop + unload-drained lifecycle now and mint RecvSignal in a later wire-neutral or next-epoch cycle. Confirm consume stays out of v0.15.0 scope.
- IdCounters.next_source_seq REMOVAL: confirmed genuinely dead (never set nonzero anywhere). RECOMMENDATION: leave it untouched this epoch to keep the change minimal (its removal would be a snapshot wire change with no behavioral payoff); schedule a separate wire-neutral cleanup. Confirm we do NOT bundle its removal into the epoch.
- SUBMIT BECOMES WAL-MUTATING: under CIL, submit() now appends an append_submit record (previously submit was WAL-silent; only committed steps appended). This interleaves Submit and Step records and changes ReplayReport.records_replayed semantics (records != committed steps). RECOMMENDATION: accept (it is intrinsic to recording exogenous inputs) and rename/clarify the ReplayReport counters (e.g. submits_replayed + steps_replayed). Confirm the counter-contract change is acceptable for downstream consumers.
